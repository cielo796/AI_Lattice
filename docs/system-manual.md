# AI Lattice システムマニュアル

最終更新: 2026-09-28

このマニュアルは、AI Lattice を利用・管理する方向けの操作ガイドです。  
アプリ作成、レコード運用、承認、ワークフロー、管理機能の基本的な使い方をまとめています。

## 1. システム概要

AI Lattice は、業務アプリを作成し、テーブル・フォーム・ビュー・レコード・承認・ワークフローを管理するためのローコード業務基盤です。

主な機能は次の通りです。

- AI ビルダーによる新規アプリ作成
- テーブル、フィールド、フォーム、ビューの設計
- レコードの登録、編集、コメント、添付ファイル管理
- アプリ単位の承認設定
- ワークフローによる自動化
- ユーザー、ロール、権限管理
- 通知、監査ログ、AI 実行ログの確認
- OpenAI 設定、Prompt Template 管理

## 2. 基本ナビゲーション

### 初回登録とログイン

設置直後は `/setup` から組織と最初の管理者を登録します。設置担当者から受け取った初期設定トークン、組織名・組織コード、管理者の名前・メールアドレス・12文字以上のパスワードを入力してください。初期設定は一度だけ実行できます。導入担当者向けの環境設定は `app/README.md` に記載しています。

登録したメールアドレスとパスワードでログインします。同じメールアドレスを複数の組織で使用している場合は、ログイン画面の「組織コードを指定する」を開いてください。

プロフィール画面ではパスワードを変更できます。現在のパスワードによる確認後、全端末のセッションが失効するため、新しいパスワードでログインし直してください。

### ナビゲーション

左サイドバーから主要画面へ移動します。

| メニュー | 用途 |

| アプリ承認 | 選択中アプリの承認一覧 |
| テーブル | アプリのテーブル、フィールド、ビュー、フォーム設計 |
| ワークフロー | 自動化ワークフローの作成・編集 |
| アプリ設定 | アプリ名、公開、承認設定など |
| 権限設計 | アプリ単位の権限設定 |
| 承認 | テナント全体の承認一覧 |
| 通知 | 自分宛て通知 |
| ユーザー管理 | ユーザー管理 |

## 3. アプリを作成する

1. 左サイドバーの `作成` または `/apps/new/ai` を開きます。
2. 作りたい業務アプリの内容を入力します。
3. AI がアプリ構成案を生成します。
4. 内容を確認してアプリを作成します。
5. 作成後、必要に応じて `テーブル` 画面でフィールドやビューを調整します。

入力例:

```text
経費申請システムを作成してください。
申請者、金額、用途、添付ファイル、承認ステータスを管理したいです。
```

## 4. テーブル・フィールドを設計する

対象アプリを選択し、左サイドバーの `テーブル` を開きます。

### テーブル

テーブルは、レコードを保存する単位です。  
例: 経費申請、顧客、案件、問い合わせ、タスク。

### フィールド

フィールドは、テーブル内の項目です。

利用できる主なフィールド種別:

| 種別 | 用途 |
| --- | --- |
| テキスト | 短い文字列 |
| 長文テキスト | 備考、説明 |
| 数値 | 金額、数量、点数 |
| 日付 | 申請日、期限 |
| 日時 | 開始日時、完了日時 |
| 真偽値 | チェック項目 |
| 選択式 | ステータス、カテゴリ |
| ユーザー参照 | 担当者、申請者 |
| 他テーブル参照 | マスタ参照、関連レコード |
| ファイル | 添付ファイル |
| AI 生成 | AI による要約・分類など |
| 計算式 | 他項目から計算する値 |

### ビュー

ビューは、レコードの見え方や絞り込み条件です。

主なビュー種別:

- 一覧
- カンバン
- カレンダー
- チャート
- 集計

承認機能を使う場合は、`アプリ設定 > 承認設定 > ステータスViewを作成` から、承認待ち・承認済み・却下・差戻し用のビューを自動作成できます。

### フォーム

フォームは、レコード登録・編集時の入力画面です。  
業務担当者が使いやすいように、表示項目や入力順を調整します。

## 5. レコードを運用する

対象アプリの実行画面からテーブルを開き、レコードを操作します。

主な操作:

- レコード作成
- レコード編集
- レコード削除
- コメント追加
- 添付ファイル追加
- 関連レコード確認
- AI アクション実行
- 承認申請

レコード詳細画面では、コメント・添付・承認履歴・関連レコードを確認できます。

## 6. 承認機能を設定する

承認は基本的にアプリに紐づきます。  
対象アプリの `アプリ設定` から設定します。

### 6.1 承認設定を開く

1. 対象アプリを選択します。
2. 左サイドバーの `アプリ設定` を開きます。
3. `承認設定` セクションを確認します。

### 6.2 承認を有効化する

`このアプリで承認を有効にする` を ON にします。

承認を有効にする場合、最低 1 名以上の承認者が必要です。

### 6.3 対象テーブルを選ぶ

`対象テーブル` で、承認対象にするテーブルを選択します。

例:

- 経費申請
- 契約申請
- 稟議
- 変更申請

### 6.4 承認方式を選ぶ

| 承認方式 | 内容 |
| --- | --- |
| 1名の承認で完了 | 承認者のうち 1 名が承認すれば承認完了 |
| 全員の承認で完了 | 全承認者が承認すると承認完了 |
| 設定順に承認 | 設定順に承認を進める |
| 指定人数の承認で完了 | 指定人数以上が承認すると承認完了 |

`定足数で承認` を選ぶ場合は、`定足数` を設定します。

### 6.5 承認者を設定する

承認者は複数設定できます。

設定方法:

- `承認者ユーザー` でユーザーを選択し、`追加` で承認者に加える
- `ロール承認者` で承認者ロールを選択する

選択済みユーザーは一覧に表示され、不要なユーザーは `×` ボタンで外せます。

ロール承認者を使う場合、そのロールに所属しているユーザーが承認者として展開されます。

よく使うロール例:

- 承認者
- アプリ管理者
- テナント管理者

### 6.6 ステータスを設定する

承認処理に応じて、レコードのステータスが変更されます。

| 項目 | 既定値 | 用途 |
| --- | --- | --- |
| 承認待ち | `pending_approval` | 承認申請後 |
| 承認済み | `approved` | 承認完了後 |
| 却下 | `rejected` | 却下後 |
| 差戻し | `returned` | 差戻し後 |

業務に合わせて、次のような値に変更できます。

```text
pending_manager_approval
finance_review
approved_for_payment
needs_revision
```

### 6.7 申請タイトル・本文テンプレートを設定する

承認依頼の件名と本文をテンプレート化できます。  
ここで設定した内容は、承認者の承認画面や通知に表示されます。

利用できる主な変数:

| 変数 | 内容 |
| --- | --- |
| `{{appCode}}` | アプリコード |
| `{{tableCode}}` | テーブルコード |
| `{{tableName}}` | テーブル名 |
| `{{recordId}}` | レコードID |
| `{{recordTitle}}` | レコードタイトル |

件名の例:

```text
{{recordTitle}} の承認依頼
```

本文の例:

```text
{{tableName}}「{{recordTitle}}」の内容を確認し、判断してください。
```

### 6.8 承認後のレコード変更JSONを設定する

承認、却下、差戻しのタイミングで、レコードデータを追加更新できます。

例: 承認時にフラグを立てる

```json
{
  "approved": true,
  "approval_note": "承認済み"
}
```

例: 差戻し時に再提出フラグを立てる

```json
{
  "needs_revision": true
}
```

入力するJSONは、レコードの `data` にマージされます。  
ステータス自体は、承認設定の `承認済み`、`却下`、`差戻し` の値が使われます。

### 6.9 ステータスViewを作成する

`ステータスViewを作成` を押すと、対象テーブルに次のビューが作成されます。

- 承認待ち
- 承認済み
- 却下
- 差戻し

これにより、承認状態別にレコードを確認できます。

### 6.10 承認設定を保存する

設定が終わったら `承認設定を保存` を押します。

保存後、レコード詳細画面から承認申請できるようになります。

## 7. 承認を申請する

1. 対象アプリの実行画面を開きます。
2. 対象テーブルを開きます。
3. 承認したいレコードを選択します。
4. レコード詳細の `Request approval` を押します。
5. 承認申請が作成され、承認者へ通知されます。
6. レコードステータスが `承認待ち` に変わります。

すでに承認待ちの申請がある場合、二重申請はできません。

## 8. 承認を処理する

承認者は次の画面から承認処理を行います。

- アプリ単位: `アプリ承認`
- 全体管理: `承認`

承認者ができる操作:

| 操作 | 結果 |
| --- | --- |
| 承認 | 承認方式の条件を満たすとレコードが承認済みになる |
| 却下 | レコードが却下ステータスになる |
| 差戻し | レコードが差戻しステータスになる |

複数承認者の場合:

- `いずれか1名が承認`: 1 名の承認で完了
- `全員が承認`: 全員の承認で完了
- `順番に承認`: 前の承認者が承認するまで次に進まない
- `定足数で承認`: 指定人数に達すると完了

却下または差戻しは、原則としてその時点で最終判断になります。

## 9. ワークフローを設定する

ワークフローは、レコード操作やスケジュールをきっかけに自動処理を実行する機能です。

対象アプリの `ワークフロー` から編集します。

### 主なノード

| ノード | 用途 |
| --- | --- |
| トリガー | レコード作成・更新・ステータス変更などの開始条件 |
| 条件分岐 | 条件に応じて後続処理を分岐 |
| 承認 | ワークフロー内で承認依頼を作成 |
| 通知 | 関係者へ通知 |
| ステータス更新 | レコードステータスを変更 |
| API Call | 外部API連携 |
| AI Action | AI要約、次アクション提案など |

### アプリ承認との違い

| 種類 | 特徴 |
| --- | --- |
| アプリ承認 | アプリ設定で定義し、レコード詳細から申請する |
| ワークフロー承認 | ワークフロー内の承認ノードで自動的に申請する |

基本的な業務承認は `アプリ承認` を使い、条件分岐や自動処理と組み合わせたい場合は `ワークフロー承認` を使います。

## 10. 権限を設定する

アプリ単位の権限は `権限設計` から管理します。

主な権限カテゴリ:

- アプリ
- テーブル
- レコード
- ワークフロー
- 承認
- 管理機能

ユーザーへ直接権限を与えるより、ロールを作成してユーザーへ割り当てる運用を推奨します。

## 11. ユーザー・ロール管理

### ユーザー管理

`ユーザー管理` では、テナント内のユーザーを管理します。

「ユーザーを追加」から表示名、メールアドレス、12文字以上の初期パスワード、組織全体に適用するロールを指定します。作成にはユーザー管理とロール管理の両方の権限が必要です。初期選択は閲覧者ロールです。初期パスワードを本人に安全に伝え、プロフィール画面で変更してもらってください。メール招待・パスワード再発行はまだありません。

ユーザーを無効化すると既存セッションも失効し、再ログインできなくなります。自分自身は無効化できません。

確認・管理する項目:

- ユーザー名
- メールアドレス
- ステータス
- 所属ロール

### ロール管理

`ロール管理` では、権限セットを定義します。

よく使うロール例:

- テナント管理者
- アプリ管理者
- 承認者
- 一般ユーザー
- 閲覧者

承認機能でロール承認者を使う場合、対象ロールにユーザーを割り当てておきます。

## 12. 通知

`通知` では、自分宛ての通知を確認できます。

通知される主なイベント:

- 承認依頼
- ワークフロー通知
- AI 処理結果
- その他システム通知

承認依頼の通知から、該当アプリの承認画面へ移動できます。

## 13. AI 機能

AI Lattice では、OpenAI 設定と Prompt Template を使って、AI 機能を利用できます。

主な利用箇所:

- AI ビルダーによるアプリ生成
- レコード詳細での AI アクション
- ワークフローの AI Action ノード
- Prompt Template によるプロンプト管理

### OpenAI 設定

`OpenAI 設定` で API 設定を管理します。  
API キーやモデル設定は、テナントの運用ルールに従って設定してください。

### AI 実行ログ

`AI実行ログ` では、AI 処理の履歴、成功・失敗、利用モデルなどを確認できます。

## 14. 監査ログ

`監査ログ` では、ユーザー操作や管理操作の履歴を確認できます。

確認できる主な情報:

- 操作日時
- 操作者
- 操作種別
- 対象リソース
- 成功・失敗
- 詳細情報

承認設定の変更、承認申請、承認判断なども監査対象です。

## 15. アプリを公開する

`アプリ設定` の `公開とバージョン管理` から公開できます。

公開すると、現在のアプリ定義がバージョンとして保存されます。

公開前に確認すること:

- テーブル・フィールド定義
- フォーム設定
- ビュー設定
- 承認設定
- ワークフロー設定
- 権限設定

## 16. よくあるトラブル

### 承認申請できない

確認項目:

- アプリ設定で承認が有効になっているか
- 対象テーブルが正しいか
- 承認者が 1 名以上設定されているか
- ロール承認者を使う場合、該当ロールにユーザーがいるか
- すでに同じレコードに承認待ち申請がないか

### 承認者に通知されない

確認項目:

- 承認者ユーザーが有効状態か
- ロール承認者のロール割り当てが正しいか
- 通知画面に表示されているか
- 監査ログにエラーが出ていないか

### ステータス別ビューにレコードが出ない

確認項目:

- `ステータスViewを作成` を実行したか
- 承認設定のステータス値とレコードステータスが一致しているか
- 対象テーブルが正しいか

### ワークフローが動かない

確認項目:

- ワークフローが active になっているか
- トリガー条件が実際の操作と一致しているか
- 条件分岐で止まっていないか
- 監査ログまたは AI 実行ログにエラーがないか

## 17. 開発・運用者向け補足

### 開発サーバー起動

`app` ディレクトリで実行します。

```powershell
npm run dev
```

ブラウザで次を開きます。

```text
http://localhost:3000
```

### Prisma Client 生成

Prisma schema を変更した場合に実行します。

```powershell
npx prisma generate
```

### Prisma migration 適用

マイグレーションをDBへ適用します。

```powershell
npx prisma migrate deploy
```

### Prisma 状態確認

```powershell
npx prisma migrate status
npx prisma validate
```

### 品質確認

```powershell
npm run check:mojibake
npm run lint
npm test
npx tsc --noEmit --pretty false
```
